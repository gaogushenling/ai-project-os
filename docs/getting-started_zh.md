# AI Project OS 入门指南

[English](./getting-started.md) | **中文**

AI Project OS 为现有项目或产品工作区增加一层轻量、可移植的 AI 协作能力，让 AI 从项目自身读取事实、任务路由、有效记忆、能力状态和交付检查。协作层根目录可以包含多个独立 Git 仓库；它不替代各仓库的项目文档、Git 工作流或工程规范。

## 使用前准备

- Python 3.11 或更高版本
- AI 可以访问本仓库，或本仓库与目标项目位于同一台机器
- 对目标项目具有读取权限
- 写入前确认目标工作区是干净的，或已了解其中的现有改动
- 完整接入需要协作层根目录拥有自己的 Git 仓库，并为共享记录形成已审查的本地提交

初始化器只准备文件，不会执行 `git init`、重组 Git 仓库、安装可选工具、启用 MCP Server 或连接生产系统。协作层根目录没有 Git 时，可以预演或准备文件，但不能宣称已完成完整接入。

## 把这个仓库交给 AI

这是推荐方式。将本仓库与需要接入的项目一起交给 AI，然后告诉它：

> 请帮我在这个项目中接入 AI Project OS。先只读检查，推荐合适的作用范围，展示预演结果，只在会实质影响结果时让我决策。

AI 应该：

1. 阅读本指南和仓库根目录的 `AGENTS.md`。
2. 在不修改目标项目的前提下完成检查。
3. 识别已有 Git 根目录、已跟踪或被忽略的嵌套仓库、项目指令、祖先及相关子目录中的 `docs/ai/`、Submodule、工作区改动和真实产品边界。
4. 复用覆盖该范围的已有协作层，或为整个产品推荐一个初始化根目录，并解释共享事实与仓库专属事实分别放在哪里。不能仅因子目录有独立 Git 就逐个初始化。
5. 说明生成文件、当前限制和回退方式，以及所属 Git 仓库和跟踪范围。根目录已有 Git 时复用；没有时将建立 Git 明确纳入接入计划。
6. 执行预演。
7. 只在目标目录、事实权威边界、覆盖行为或 Git 组织方式存在真实选择时询问用户。用户已明确要求父目录建立 Git，即已授权已确认计划中的这一步，不要重复索取同一授权。
8. 按授权补齐所属 Git 仓库，范围明确后初始化，验证文件及跟踪边界，并说明日常使用方式。尚未提交的事项单独报告；仅生成文件或执行 `git init` 不会形成已记录的版本。

AI 可以依据检查结果自行决定安全、可恢复的细节，但不能静默重组 Git 仓库、覆盖已有指令、把本机路径写入提交文件或启用可选能力。

## 手动接入

克隆并进入本仓库：

```powershell
git clone https://github.com/gaogushenling/ai-project-os.git
cd ai-project-os
```

下面的命令从本接入工具仓库运行，`--target` 指向已确认的协作层根目录。在其他目录工作时，使用解析后的脚本和目标路径；初始化不会将这些维护脚本复制进目标项目。写入前先预览全部计划文件：

```powershell
python scripts/init_project_os.py --target <project-root> --dry-run
```

确认预演结果后初始化：

```powershell
python scripts/init_project_os.py --target <project-root>
```

初始化器默认保留已有文件。在确认 `--force` 会刷新哪些模板和协议文件之前，不要使用它。祖先目录已有协作层时，它也会拒绝在下面新建第二份，`--force` 和 `--dry-run` 都不能绕过。仅当嵌套目录是有意独立管理的项目时才使用 `--allow-nested`；该选项不会合并现有协作层。

## 选择项目根目录

### 单仓库

单个仓库承载独立产品时，使用其 Git 仓库根目录作为 `<project-root>`。如果它已经属于有共享协作层的产品工作区，则复用共享层。生成文件可以跟随所属仓库提交。

### 多仓库工作区

同一产品的多个仓库位于共同父目录时，优先只在该父目录放一份协作层，并由父目录自己的 Git 仓库记录共享资料的版本。协作层根目录是产品和上下文边界，子 Git 仓库保留代码和独立历史。父目录已有 Git 时复用；没有时，将建立 Git 纳入明确授权的接入计划。不能为了减少文件数量，把存放多个无关项目的大目录当成一个工作区。

例如，只初始化 `product-workspace/`：

```text
product-workspace/
  .git/                       # 共享记录和选定的工作区文档
  .gitignore                  # 排除完整子仓库目录
  AGENTS.md
  .agents/skills/project-memory/SKILL.md
  docs/ai/                     # 唯一共享协作层
  api/.git/                    # 独立代码仓库
  web/.git/                    # 独立代码仓库
```

明确区分数据归属和执行位置：

- 产品身份、仓库角色、跨仓决策、记忆和共同验收规则放在父层。`docs/ai/project.json` 中将父仓库记录为 `{"path": ".", "role": "workspace-control"}`，再加入 `{"path": "api", "role": "backend"}`、`{"path": "web", "role": "frontend"}` 等子仓库。角色应来自核实，不将模板中的 `.` 继续标为主代码仓库。
- 仓库专属事实可按需放在 `docs/ai/repositories/api.json`、`web.json`，只由命中的路由加载。子仓库已有指令、README 和代码保留在原位置，通过路由引用，不复制整份内容。
- 每个仓库命令明确相对工作区的执行目录，例如 `{"command": "npm test", "cwd": "web"}`。不能在父目录直接执行子仓库命令，也不能假定多个仓库共用工具和验证状态。这里仅展示格式，不代表命令已经核实。
- Git 状态、差异、提交和历史检查在所属仓库执行：共享记录在父仓库，代码在各子仓库。父 Git 不会自动锁定子仓库版本，也不会合并它们的历史。
- 可移植路径相对协作层根目录；本机检出映射保持仅本地使用。路由不能越出根目录，通过符号链接越界也不允许。

日常使用优先在父工作区打开 AI。从子 Git 根单独启动时，不保证会发现仅放在父目录的文件。例如 Codex 通常只在检测到的项目/Git 范围内发现指令和 Skill（[AGENTS.md 发现规则](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Skill 发现规则](https://learn.chatgpt.com/docs/build-skills)）。需要独立进入子仓库时，显式读取父级 `AGENTS.md` 和记忆入口，或有意增加保留原生子仓规则的轻量相对指针。指针不是第二次初始化，也不会使父级 MCP 配置自动可用；需要另行核实所用工具的配置发现规则及信任状态。

父目录尚无 Git 时，生成文件只算准备工作；完成完整接入前，应按授权建立父 Git 仓库。初始化器不会代为执行这一步。不能顺带移动检出目录或将子仓库转换为 Submodule。无关产品或有意独立使用的项目仍适合分别初始化。

### 安全记录共享工作区的版本

父仓库默认只跟踪共享 AI 层、其忽略规则和用户选定的工作区文档。使用根目录锚定的忽略项排除完整独立子仓库；父层仍可通过路由读取子仓库文件，各子仓库继续管理代码历史。

写入前先核实选定的产品边界和真实 Git 根。下面以 `api`、`web` 为例展示只读检查，使用时替换为已核实的目录名：

```powershell
git -C <project-root> rev-parse --show-toplevel
git -C <project-root> status --short
git -C <project-root> ls-files --stage
git -C <project-root> ls-files --stage -- api web
git -C <project-root>/api rev-parse --show-toplevel
git -C <project-root>/api status --short
git -C <project-root>/web rev-parse --show-toplevel
git -C <project-root>/web status --short
```

父目录没有 Git 时，对它的 Git 检查可能失败；若解析到祖先 Git 根，也不代表选定根目录已拥有自己的仓库。父仓库已经跟踪子目录文件或存在模式为 `160000` 的 gitlink 时，先记录证据，解决跟踪范围和拓扑选择，再修改索引。添加忽略规则不会取消已有跟踪。有意采用的现有 Submodule 应保留其已授权拓扑，不能为了满足下文独立子仓库范例而移除 gitlink。

先按上文从本接入工具仓库执行初始化器预演。只有范围和父 Git 计划已确认，且根目录没有自己的 Git 仓库时，才执行：

```powershell
git -C <project-root> init
```

随后从接入工具仓库运行初始化器，补全核实过的事实，并在父 `.gitignore` 中添加以下规则，保留已有规则。目录名以实际子仓库为准，并检查后面的规则是否会覆盖这些排除项：

```gitignore
/api/
/web/
```

检查完整文件清单，包括未跟踪文件和日志，排除私有资料及本机检出映射。暂存前确认子目录已被忽略，再只暂存核实过的共享层路径和忽略文件；用户选定的工作区文档另用准确路径添加：

```powershell
git -C <project-root> check-ignore -- api/ web/
git -C <project-root> add -- .gitignore AGENTS.md .agents/skills/project-memory/SKILL.md docs/ai
git -C <project-root> diff --cached --name-status
git -C <project-root> diff --cached
git -C <project-root> ls-files --stage
git -C <project-root> ls-files --stage -- api web
```

不要使用 `git add .`，也不要强行添加子目录。在这种独立子仓库布局中，最终父索引不能包含 `160000` gitlink 或子仓库代码，最后一条命令必须没有输出。提交前审查全部暂存内容。用户要求以父 Git 记录协作层时，已授权在确认范围内完成经审查的本地记录，按项目提交流程执行，不重复询问；远端创建、配置及推送仍需相应授权。例如审查后执行：

```powershell
git -C <project-root> commit -m "Initialize shared AI collaboration layer"
git -C <project-root> show --stat --oneline HEAD
git -C <project-root> status --short
```

核对本地提交只包含预期共享记录。缺少 Git 身份或项目规则禁止提交时，报告“版本记录待完成”，不修改全局身份，也不把 `git init` 当作已有历史；形成已记录版本前，完整接入仍待完成。

父 Git 记录共享事实的版本，不能保证克隆父仓库即可复现子仓库，也不会锁定其版本。确有版本锁定需求时，由用户明确选择版本清单或 Submodule 流程，不自动改变仓库结构。

### Git Submodule

当父仓库需要锁定并复现子仓库的准确版本时，可以使用 Submodule。它也会增加克隆、分支切换、更新、CI 和 detached HEAD 等操作成本，需要团队明确管理方式。

AI Project OS 可以描述已有的 Submodule 结构，但没有用户明确要求时，不能把现有仓库自动转换为 Submodule。

### 被父仓库忽略的嵌套仓库

子仓库保留独立历史时，父 Git 默认忽略完整子仓库目录，记录共享协作层和选定工作区文档。它不会自动记录子仓库的远端和版本，所以只克隆父仓库无法复现完整工作区。

应把它当成本地组织方式，不能据此认定父仓库拥有或管理子仓库版本。提交文件只记录可移植的逻辑角色，本地检出映射保持忽略。

位于初始化根目录之外的独立同级仓库仍超出当前路由安全边界。同一产品可在范围已授权的前提下，初始化前选择合适的共同父目录；否则只记录逻辑关系或使用独立层。不要添加越过根目录的路由目标。

### 合并已有的子目录协作层

父层初始化会保留已有文件，不会自动迁移或删除子层。合并前应：

1. 从当前文件清点并备份所有子层、指令改动、能力清单/锁文件及忽略规则增量。分别检查子仓库工作区和索引；未跟踪或未提交文件也可能包含有价值的已核实事实。只备份 `HEAD` 不能保留这些状态。
2. 对已确认的父目录先预演，按授权建立所属 Git 仓库和子仓库忽略项，再初始化。共享事实只保留一份；仓库专属事实、来源、验证日期和记忆应保留，并明确所属仓库。
3. 将文件引用和命令工作目录改为相对父目录。旧的 `cwd: "."` 应改为所属子目录；逐项检查结构化路径，不盲目全文替换。先解决指令冲突、重复能力 ID 或不同锁定版本，再决定共享配置。
4. 校验父层，并检查相关路由和命令目录；在实际使用中验证 AI 如何加载父入口。协作层校验不能证明业务构建通过或工具已连接。
5. 迁移和删除范围获授权后，才移除已确认冗余的协作层文件和失效指令段落。保留子仓原生规则及无关的 `docs/`、Skill、配置和忽略项；需要子仓独立会话时可以保留轻量指针。

父层验收前保留备份。回退时根据清单恢复改动过的协作层文件和指令/忽略增量，不重置子仓库或改写历史。

## 补全生成的项目事实

初始化后检查以下文件：

- `docs/ai/project.json`：产品身份、负责人、事实来源、仓库、命令、质量门禁和确认边界
- `docs/ai/routes.json`：任务信号、按需加载的文件和交付门禁
- `docs/ai/memory.json`：会影响未来执行的已验证失败和纠偏
- `docs/ai/capabilities.json`：项目级 Skill、MCP 位置和已安装能力状态
- `AGENTS.md`：兼容 AI 都可以读取的简洁项目协议

用经过核实的项目事实替换相关 `TODO` 占位符。密钥、凭据、个人路径和临时观察不得写入提交文件。

验证结果：

```powershell
python scripts/validate_project_os.py --target <project-root>
```

所有占位信息都已按项目实际情况补全后，使用严格模式：

```powershell
python scripts/validate_project_os.py --target <project-root> --strict
```

检查所属 Git 仓库的暂存差异和跟踪边界；得到提交授权后，只提交审查过的共享层文件和选定工作区文档。缺少所属 Git 或尚未形成首个提交时应明确报告；只准备文件或通过文件校验，不代表已有版本历史。

## 日常使用

在协作层根目录启动 AI（共享工作区使用父目录）并直接描述任务。入口加载后，兼容的 Agent 会自动应用项目 `AGENTS.md`、进入项目记忆并匹配任务路由。仅在子仓库启动的会话可能需要按上文显式加载父入口。例如：

> 调查这个需求。只加载相关项目事实，定义最小完整结果，并在交付前说明验证证据。

工作过程中，AI 应该：

1. 阅读项目的 `AGENTS.md`。
2. 通过 `.agents/skills/project-memory/SKILL.md` 进入项目记忆。
3. 在 `docs/ai/routes.json` 中匹配任务，只加载列出的文件。
4. 使用 `docs/ai/project.json` 和路由到的仓库事实中记录的命令和边界；文件路径相对协作层根目录解析，命令在声明的工作目录执行。
5. 只记录会改变后续执行方式的失败或纠偏。
6. 在最终回执中区分代码实现、工程验证和产品验收。

项目发生变化时更新对应事实。不要把项目记忆当成聊天记录或通用文档堆放区。

## 更新已初始化项目

拉取或下载新版 AI Project OS，对已初始化项目执行 `--dry-run` 并检查新增建议。正常重复运行会保留已有文件和已填写状态；`--force` 会刷新模板和协议文件，但仍保护 `docs/ai/` 下已填写的状态文件，合并时要保留有意的本地修改。

更新后始终重新验证。已安装的第三方 Skill 和托管 MCP 配置块会与锁文件哈希进行比较。

## 回退与卸载

项目初始化可能保留或复用原本就存在的文件，因此不提供自动卸载命令。应结合所属 Git 仓库的证据、接入前清单及当前文件备份，只撤销接入过程实际产生的改动。若只进行了非 Git 文件准备，则使用对应清单和备份；这不算完整接入：

1. 删除任何内容前先检查 `git status`、已暂存和未暂存差异及未跟踪文件。保留接入前已有的未提交事实；恢复 `HEAD` 不会恢复这些事实。
2. 如果接入改动尚未提交，只删除预演中明确标记为新建的文件；对于原有文件中的追加内容，应手工撤销，不能删除接入前已经存在的整个文件。
3. 如果接入已经形成独立提交，优先执行 `git revert <adoption-commit>`，保留共享历史并确保改动可恢复。
4. 如需重置已填写的项目状态，先按需备份，再删除 `docs/ai/` 下对应状态文件并重新初始化以生成默认值。删除状态会永久丢弃已记录的项目事实、记忆、能力清单或锁定数据。
5. 已安装 Skill 或托管 MCP 配置块需要根据 `docs/ai/capabilities.json` 和 `docs/ai/capabilities.lock.json` 记录的归属单独移除。删除核心协作层不会自动撤销外部工具或服务。

回退或卸载后，重新运行相关项目检查并检查最终 Git 差异。正常卸载不应使用历史改写或破坏性重置。

## 安全边界

- 推荐不等于安装，安装不等于启用，启用也不代表获得外部或生产操作授权。
- 核对权威性和时效性后，项目已有指令与事实优先于通用示例。
- 生产变更、破坏性数据操作、凭据、外部写入和数据库变更需要单独授权。
- 路由目标必须位于初始化项目根目录内。
- 可移植的提交文件不能包含密钥或本机绝对路径。
- 建立父 Git 仓库并记录经审查的本地版本必须在授权范围内；用户要求以父 Git 记录协作层已覆盖这两步，远端设置、推送、Submodule 转换及跟踪额外文档仍分别需要相应授权。

## 故障处理

### 预演提示文件已经存在

阅读已有内容，决定保留、手工合并 AI Project OS 协议，还是对允许刷新的模板使用 `--force`。不能盲目覆盖项目指令。

### 严格校验提示占位信息未填写

使用核实过的项目事实填写对应字段。如果信息确实未知，继续使用普通校验并报告未填写项，不要编造答案。

### 路由目标位于项目之外

同一产品的多个仓库应在初始化前选择共同父目录作为协作层根；其他情况将可移植事实移入当前根目录、使用独立层或只记录逻辑关系。不能用绝对路径或符号链接绕过路由安全检查。

### 初始化器发现祖先已有协作层

更新或校验共享层时，使用该层根目录作为 `--target`，再按需要路由到子仓库。`--force` 不能扩大作用范围。如果嵌套目录确实是独立产品，先明确选择独立管理范围，再使用 `--allow-nested`。

### AI 没有自动调用 Skill

让 AI 阅读项目的 `AGENTS.md` 和 `.agents/skills/project-memory/SKILL.md`，或明确说“使用 `$ai-project-os`”。不同工具的 Skill 支持程度不同，但只要能读取文件，任何 AI 都能使用已提交的项目事实。

### 能力无法连接

检查项目能力清单、本地命令是否存在以及要求的环境变量名称。不能为了连接成功而把密钥值粘贴进 `docs/ai/` 或提示词。

## 接入验收清单

- 初始化根目录和事实负责人明确。
- 协作层根目录拥有自己的 Git 仓库；预期共享记录已有版本，或明确报告尚待首个提交。
- 父仓库跟踪范围已核实。默认独立子仓库布局中，子目录被忽略，父索引不包含子代码或 `160000` gitlink。
- 已有指令得到保留或经过有意合并。
- 普通校验通过；占位信息补全后使用严格校验。
- 命令和质量门禁来自验证，不是猜测。
- 多仓库角色使用可移植的逻辑描述。
- 提交文件不包含密钥或本机绝对路径。
- 用户知道如何调用 AI Project OS，也知道后续事实应该记录在哪里。
